# Memory policy review for ChatGPTKernel

Status: source review with a user-reported runtime observation dated 2026-10-23. No candidate device benchmark, boot test, thermal measurement, or improvement is claimed by this document.

The target is a Redmi Note 12 with 4 GB RAM, Android 13 / unofficial LineageOS 20, and a working Zepharo R10 kernel. Preserve the ROM, vendor modules, root integration, and Android's process priorities. The source baseline is `topnotchfreaks/kernel_msm-5.15` at `d246c8c17548bb1a2756092cabf34d11eedcde8c` (Linux 5.15.216).

## Evidence and limits

The reported workload has approximately 74% memory PSI `some`, 36% `full`, approximately 600 MiB `MemAvailable`, and a 3 GiB logical zRAM device occupying approximately 1 GiB RAM. These observations support investigating reclaim stalls. They do not establish whether the bottleneck is file refaults, hot anonymous pages, compression CPU time, storage, or an app's main thread. A full logical swap device also does not mean zRAM occupies 3 GiB physical RAM. Use `mm_stat` to separate original bytes, compressed bytes, and total allocator usage [S6].

On 2026-10-23, the user reported `cat /sys/kernel/mm/lru_gen/enabled` returning `0x0000` on the current R10 installation. This confirms that MGLRU's core was disabled at that observation. It makes enabling the existing reclaim algorithm a concrete behavioral change to evaluate, rather than assuming it was already active. The readback does not establish whether the disabled state came solely from the build default or a later startup override.

The previous lower lmkd thrashing threshold gave only a temporary minor benefit. There is no evidence that increasing killing aggressiveness again will meet the user's requirement to retain the existing apps and services.

R10's `unified_defconfig` already enables PSI, MGLRU support, zRAM, LZ4KD, DAMON support, and THP in `madvise` mode [S1]. These features must not be advertised as newly added. The effective configuration still needs to be resolved from the real build recipe and fragments. The release Image's embedded IKCONFIG disagrees with its actual compiler and some included functions; it is not a reliable replacement for that recipe.

## Decision matrix

`Apply` means an isolated candidate change, subject to verifying the generated configuration. `Keep` means preserve the working baseline and ROM policy. `Reject` means exclude from this package. `Defer` means require device evidence before selecting a new value.

| Decision | Candidate | Expected benefit and evidence | Cost / reason on this 4 GB device |
| --- | --- | --- | --- |
| Apply, conditional on generated config | Set `CONFIG_LRU_GEN_ENABLED=y` if the resolved baseline does not already enable it | The user confirmed runtime `0x0000` on 2026-10-23. Enabling R10's existing MGLRU therefore targets an inactive reclaim algorithm, with a documented runtime switch [S2, S3]. | Aging and page-table walks consume CPU. It can help when useful cold pages exist; it cannot fit an all-hot working set into insufficient RAM. Confirm bit `0x1` is active after boot, since startup policy can override the build default. No improvement magnitude is established. |
| Keep | `CONFIG_LRU_GEN=y`, standard capability handling | Keeps the kernel's existing supported implementation. The documented `y` switch enables capabilities that the hardware supports [S2, S3]. | Do not require a readback of `0x0007`: unsupported hardware capabilities are masked from the reported value. Bit `0x1` identifies the active core. |
| Keep | MGLRU `min_ttl_ms=0` | Zero is the documented disabled default for its additional working-set protection [S2]. | A positive TTL can invoke the kernel OOM killer when the protected working set cannot fit. That is an undesirable way to retain TikTok plus existing background services on 4 GB. |
| Keep | PSI, memcg, refault and active/inactive accounting | Android 13 lmkd observes pressure, scan activity, refaults and file-LRU sizes. R10's MGLRU maintains these source interfaces [S4, S5, A1]. | Avoid disabling PSI for a claimed reduction in overhead or replacing Android's memory controller. The diagnostic and pressure response are valuable during this workload. |
| Keep | Existing zRAM implementation and baseline compressor selection | `unified_defconfig` selects LZ4KD and includes LZ4/LZO/ZSTD support [S1, S7]. | The effective runtime algorithm can be selected by Android before zRAM initialization. No device measurements justify replacing LZ4KD, increasing compression effort, or claiming a faster compressor. |
| Keep | THP `madvise` baseline | Retains the working source policy [S1]. | Forcing THP `always` can add allocation/compaction work. Disabling existing THP support can affect callers that deliberately request it. Neither is justified by PSI alone. |
| Keep | Existing normal compaction and initial `compaction_proactiveness` | R10's source default is already 20; normal compaction remains useful for contiguous allocations [S8]. | Do not label an existing background mechanism as a new optimization. Runtime Android/vendor overrides remain authoritative. |
| Keep | Existing kernel swappiness default and ROM overrides | R10 `mm/vmscan.c` initializes `vm_swappiness=100`, not the generic documentation's 60. Its MGLRU also consults memcg swappiness and the Android tuning hook [S3]. | Retaining the baseline isolates the MGLRU comparison. A global constant cannot represent every app, memcg, or storage/compression cost. |
| Reject | Lower lmkd complete-stall threshold to 300 ms as a bundled optimization | This would trigger a different kill branch rather than improve reclaim efficiency [A1]. | Android 13's critical-event branch allows victims down to `oom_score_adj=0`. Foreground and perceptible app processes can become eligible after higher-adj victims are exhausted. |
| Reject | Increase proactive compaction, periodically write `compact_memory`, or force compaction at app launch | Compaction rearranges physical pages for high-order allocations; it does not create additional RAM [S8]. | The kernel explicitly documents system-wide work and possible application latency spikes. No high-order-allocation failure or compaction-stall evidence was supplied. |
| Reject | Scheduled `drop_caches`, memory cleaners, or large `vfs_cache_pressure` changes | Cache objects are already reclaimed on demand. Source documentation warns that dropping useful caches adds I/O and CPU to recreate them [S8]. | A temporary rise in free RAM is not a persistent responsiveness improvement. Refaulting TikTok/app code can worsen the observed workload. |
| Reject | Hard-coded 4–8 GiB zRAM, fixed physical zRAM caps, swapoff/reset during load | A larger logical device does not guarantee useful compressed capacity [S6]. | More swapped hot pages can add compression/decompression work and still consume RAM. Swapoff may need to materialize most existing swapped data into an already pressured device. |
| Reject | Enable storage swap or zRAM writeback automatically | R10 has writeback support as an optional configuration, with documented flash-I/O budgeting [S6, S7]. | Requires a suitable backing device and Android lifecycle policy. It can add storage latency, writes, and integration changes outside an Image-only package. |
| Defer | Change zRAM compressor or logical size | Compare currently selected algorithm, `mm_stat`, swap-in/out rates, CPU time and UI stalls first [S6, S7]. | LZ4/LZ4KD versus ZSTD is a workload-dependent CPU/capacity tradeoff. Compressor changes require a fresh uninitialized device; no live swapoff/reset is included in this project. |
| Defer | Raise/lower swappiness | Values above 100 are permitted for relatively cheap in-memory swap; the documentation explicitly requires experimentation [S8]. | High values can exchange file refaults for compression and anonymous swap churn. Low values can evict useful app code/cache sooner. Full zRAM and aggregate PSI do not select the right value. |
| Defer | Disable proactive compaction for an alternative comparison | Consider only if compaction counters and traces show appreciable work without useful high-order allocation benefit [S8]. | Disabling it may shift work to direct allocation paths. Do not assume that removing background work improves tail latency. |
| Defer | Enable DAMON_RECLAIM | Compiled support does not mean it runs. R10 initializes its enable flag to false and uses its own age, quota and watermark policy [S9]. | Adds monitoring and another reclaim policy. Its defaults target cold regions over a much longer interval than an app-start freeze. Avoid stacking it with a first MGLRU comparison. |
| Defer | Change reclaim watermarks, dirty limits, readahead or reclaim priorities | Consider only after counters/traces identify the matching bottleneck [S8]. | Larger reserves can start reclaim sooner while reducing usable headroom. Extra writeback/readahead can contend with app I/O. Arbitrary constants are not justified by the RAM size alone. |

## Proposed memory change

Use one primary memory intervention: enable R10's existing MGLRU by default, setting `CONFIG_LRU_GEN_ENABLED=y` if the resolved baseline does not already set it. The user-confirmed disabled runtime state and observed reclaim pressure justify this isolated candidate. They do not prove that it will improve this workload or resolve the ANR. Do not replace the implementation, alter its generation constants, change swappiness, add a TTL, change zRAM size/compressor, or package lmkd properties alongside it.

The recorded old runtime `/sys/kernel/mm/lru_gen/enabled` value is `0x0000` (user observation, 2026-10-23). A value whose bit `0x1` is clear means the core is disabled; other capability bits can be set independently. After a candidate boot, verify bit `0x1` is active without requiring `0x0007`. A ROM boot script may override a kernel default; if the resolved baseline was already default-on, investigate that override before claiming the configuration edit changes runtime behavior. Do not rewrite the ROM's script just to force a result.

The source supports changing the main switch at runtime. It fills or drains the old and new LRU lists in bounded batches and calls `cond_resched()` between batches [S3]. This is a supported state transition, but can create transient CPU work and latency, so compare steady workloads after the transition has settled. Saving and restoring the previously read capability value restores the effective switch configuration. This project does not issue those writes to a phone.

## Android 13 compatibility

R10 MGLRU's `lru_gen_update_size()` updates the ordinary active/inactive accounting when pages enter, leave, or change active generations [S4]. Its `lru_gen_refault()` increments `WORKINGSET_REFAULT_BASE + type` before applying generation-history tests [S5]. Therefore lmkd's file-LRU and `workingset_refault_file` inputs remain available; MGLRU's internal historical feedback is not a replacement for the exported counter. This source compatibility is not a substitute for validating the actual vendor modules and booted build.

The reviewed LineageOS 20 lmkd uses a one-second PSI monitor window. Its default critical threshold of 700 ms refers to accumulated `full` stalls in that window, not to `avg10` or `avg60`. The default partial monitor already wakes it at 70 ms, or 200 ms on low-RAM configurations. A critical event, after the earlier reclaim/refault gate, uses a victim minimum adj of zero [A1]. Hence a lower critical threshold must not be described as merely allowing more cached/background kills. Preserve these userspace settings.

## Validation and acceptance

Build checks establish the selected configuration and source interfaces; they cannot establish responsiveness on the phone. Retain the resolved baseline `.config`, generated candidate `.config`, configuration diff and build/source identity. For the memory portion, verify that only the intended MGLRU default changes and that PSI, memcg, swap, zRAM and vendor ABI settings remain intact.

Device comparison should use the same ROM, apps, modules, network conditions and approximate thermal starting point, with the same app-launch/scroll/background-app sequence repeated several times. Give the reclaim algorithm a comparable warm-up. Record:

- Whether launch/scroll freezes or ANRs recur, and whether existing WhatsApp/background services remain usable.
- Memory PSI totals over measured intervals, plus `avg10`/`avg60` for context. Derive interval stall percentage from counter delta divided by elapsed microseconds; do not interpret a smoothed average as an actual PSI trigger event.
- `/proc/vmstat` deltas for file refaults, direct/kswapd scans, swap-in/out, allocation stalls and compaction activity.
- zRAM `comp_algorithm`, `disksize`, `mm_stat` and `/proc/swaps`, separating compression ratio from total physical allocator cost [S6].
- lmkd kill reasons/victims and kernel OOMs, together with CPU load and temperature/thermal throttling context.

Accept a performance claim only if the repeated user workload improves without an unacceptable increase in app/service loss, thermal load or battery cost. If all needed memory remains hot, report the capacity limit rather than adding more unrelated policies. If memory pressure improves but the same ANR remains, inspect its main-thread trace instead of assuming another memory knob will fix it.
