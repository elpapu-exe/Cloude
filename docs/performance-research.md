# CPU, graphics, I/O and power review

Status: source review, one implemented KProfiles correctness patch and build recommendations. No phone benchmark, boot test, temperature measurement, battery measurement or TikTok improvement is claimed here. The generated configuration and complete build log remain the implementation evidence for build-policy choices.

Target: Redmi Note 12 4G with 4 GB RAM, the existing unofficial Android 13 / LineageOS 20 ROM, full TikTok, KernelSU, WaEnhancer and InstaEclipse. The baseline is Zepharo R10, Linux 5.15.216, source commit `d246c8c17548bb1a2756092cabf34d11eedcde8c` [S1]. Preserve vendor-module compatibility and Android's process/service priorities. The supplied memory PSI observations, approximately 74% `some` and 36% `full`, motivate reclaim work; they do not identify a CPU governor, graphics driver or disk scheduler as the cause of the ANR.

## Decisions

`Apply` means a concrete build check or independently reviewed correctness change. `Keep` preserves the working source/vendor policy. `Reject` excludes a change from this build. `Defer` requires evidence from the actual device before choosing another policy.

| Decision | Area / candidate | Evidence and intended behavior | Cost or reason for the decision |
| --- | --- | --- | --- |
| Apply | Record and verify the effective optimization level after `olddefconfig` | The defconfig requests `CC_OPTIMIZE_FOR_PERFORMANCE_O3`, but the same pinned tree restricts that option to `ARC`. Its ordinary ARM64 Kconfig selection is `CC_OPTIMIZE_FOR_PERFORMANCE`, mapped to `-O2` by the Makefile [S1, S2, S3]. | A requested defconfig line is not evidence that an ARM64 build used `-O3`. Do not remove the architecture dependency or add conflicting `KCFLAGS=-O3` just to make the label true. Preserve and inspect the generated `.config` and a real compile command. |
| Keep | Full Clang LTO, CFI, Shadow Call Stack and module version checking | The source defconfig already enables these [S1]. Preserve the resolved reference configuration and its toolchain constraints. | Full LTO costs build time and host RAM. Neither LTO nor disabling CFI supplies extra app RAM. Do not claim Full LTO as newly added, change LTO mode casually, or disable module/CFI protection to make incompatible objects load. |
| Keep | Kernel CPU governor selection and vendor Power HAL control | ARM64's CPUFreq Kconfig defaults to `schedutil`; SchedHorizon is an additional compiled option [S4]. A compiled governor is not proof that it is active on the phone. | Do not bundle a startup script that repeatedly overrides the ROM's governor, frequency limits, cpusets or utilization clamps. Vendor policy may change them for launches, thermals and screen state. |
| Defer | Switch from the actual active governor to SchedHorizon or another governor | SchedHorizon modifies utilization-based selection with `efficient_freq` and `up_delay` arrays [S4, S5]. That is a CPU ramp-delay policy, not a memory-pressure treatment. | A delay can reduce power or postpone CPU service. No trace identifies frequency response as the launch bottleneck. Retain the governor as an available option without declaring it faster than schedutil. |
| Defer | New `efficient_freq`, `up_delay`, up/down-rate or boost constants | The SchedHorizon Kconfig documents that frequency escalation waits for sustained demand. Its source initializes the additional arrays to `{0}` and rate limits to 500/1000 microseconds [S4, S5]. | No measured energy model or runtime policy values select new constants. Do not copy MHz or delay arrays from a different SoC. Validate the optional tunable implementation before adding automatic writes. |
| Apply: patch 0003 | Fix demonstrable KProfiles error-path locking defects | The original `kp_set_mode_rollback()` returns from an invalid-level branch while holding its mutex; `kp_set_mode()` has an analogous early return while holding its spinlock [S6]. The patch validates mode inputs before acquiring those locks. | These are correctness issues, not demonstrated TikTok speed gains. Exported signatures and accepted modes remain unchanged. |
| Apply: patch 0003 | Remove KProfiles' additional all-disk I/O override | Its original iterator converts the next device before checking for NULL, includes partition devices, compares a successful sysfs-style `count` return to zero, and bypasses the queue's normal sysfs serialization [S6, S13, S14]. | Keep the configured/default or Android-selected scheduler. Removing this unsolicited rewrite is narrower than adding a second disk-management policy or importing another scheduler. KProfiles' exported functions and mode interface remain present. |
| Apply: patch 0003 | Dispatch KProfiles blocking notifications through static work | The original `kp_set_mode()` calls a blocking notifier chain while holding a spinlock [S6]. The patch updates state under short IRQ-safe spinlocks and samples active mode in a worker before dispatching listeners. | Notifications are intentionally asynchronous; rapid transitions can coalesce. There are no per-event allocations or newly allocated workqueues. Pending work is canceled on initialization failure and module exit. The temporary-override API still sleeps and requires process context. |
| Defer pending synchronization audit | SchedHorizon dynamic-array hardening | Sysfs stores replace and free frequency/delay arrays while the frequency callback reads them; allocation, token parsing, length consistency and numeric conversion also need review [S5]. | A privileged writer and concurrent policy updates can exercise paths unrelated to normal app performance. This needs a correctness patch with a clear lifetime/locking model, not new tuning values. |
| Keep | Existing KProfiles availability and deliberate user-selected mode | The defconfig requests default mode 3 and disables automatic display-driven KProfiles. Source mode labels alone do not establish a measured CPU or battery outcome [S1, S6]. | Do not silently introduce screen-off profile switching or assume mode 2/3 is optimal. The generated config and any deliberate final default change must be recorded explicitly. Existing user modules can also set runtime policy. |
| Keep | CPU idle states, PREEMPT, scheduler/vendor hooks and Android priorities | CPU idle states exchange wake latency for idle power, and PM QoS constraints influence selection [S7]. Preserve the working baseline's interfaces. | Avoid globally disabling deep idle, forcing `idle=poll`, holding a zero CPU latency constraint, or elevating app threads to real-time scheduling. More power and heat can reduce sustained performance, and higher CPU priority cannot remove memory stalls. |
| Keep | GPU/devfreq, bandwidth and OPP policy | The defconfig includes several devfreq governors, thermal control and CPU/devfreq cooling support [S1]. That does not establish which Qualcomm vendor driver/governor is active. | No device trace or audited GPU OPP/voltage table supports a clock, governor or bandwidth change. Preserve the vendor graphics modules and their ABI. |
| Reject | GPU/CPU overclock, undervolt, permanent performance governor or forced minimum clocks | These change power, stability and thermal behavior without addressing the identified reclaim problem. | No hardware validation is available. Do not substitute a short frequency burst for evidence of improved sustained scrolling, video playback or notification delivery. |
| Keep | Thermal sensors, trip points, cooling devices and vendor thermal policy | The baseline enables thermal management and emergency-poweroff support [S1]. | Do not disable thermal services, raise trip points, fake temperature readings or bypass thermal caps. A build must preserve protection even when it cannot quantify performance. |
| Keep | Existing I/O scheduler support and initial resolved selection | R10 requests Samsung Generic (SSG) as default and includes BFQ; mq-deadline is also defined in its scheduler Kconfig [S1, S8]. Runtime selection can differ because Android/vendor code can change it. | Do not present BFQ as a new feature or replace every block queue's scheduler at boot. Check the actual target storage queue before any later comparison. |
| Defer | Make BFQ the default | BFQ offers interactive-I/O latency and fairness heuristics. Its own documentation describes additional per-request work and cases where stronger guarantees reduce throughput [S9]. | These tradeoffs do not select the best scheduler for this phone. Documented benchmark numbers from other CPUs are not Redmi Note 12 measurements. Full in-RAM zRAM does not imply flash-I/O scheduling is the dominant cost. |
| Defer | Change the active flash-storage scheduler to mq-deadline | It is already available in the source and has lower scheduling complexity than BFQ [S8, S9]. | Lower scheduler overhead does not prove better app tail latency under concurrent reads/writes. Retain availability; choose a default only after an I/O-specific bottleneck is identified. |
| Reject for this build | Import ADIOS or another external scheduler | ADIOS is absent from the pinned block-scheduler Kconfig [S8]. Importing it adds new code and integration work. | No source-specific phone evidence justifies replacing the already available schedulers. A new scheduler name is not an optimization result. |
| Keep | Storage readahead, request limits and filesystem policy | Queue readahead controls speculative reads and request limits bound queued work [S10]. | Arbitrarily increasing readahead or queue depth consumes memory or increases competing work. Do not force large readahead, discard useful caches or run periodic `drop_caches` jobs on this pressured 4 GB system. |
| Keep | THP in the existing `madvise` mode | This is already requested by the source defconfig. The kernel documentation specifically recommends opt-in huge pages for embedded systems to avoid wasted memory [S1, S11]. | Forcing `always` can expand an application's footprint; direct reclaim/compaction for huge-page allocation can stall a caller. Disabling all THP can also remove a deliberate caller's benefit. Neither change follows from aggregate PSI. |
| Keep / defer policy changes | zRAM implementation, selected compressor and Android-owned sizing | R10 includes zRAM/zsmalloc and requests LZ4KD as the default compressor [S1]. The zRAM documentation separates logical size, compressed data and total allocated physical memory [S12]. | A 3 GiB logical device using about 1 GiB physical RAM is not a 3 GiB RAM reservation. More logical swap can preserve cold data but can also prolong hot-page compression churn. Do not hard-code a larger disk, reset active swap, add storage writeback or change compressors without the evidence described in the memory review. |
| Reject | More autonomous scanners, compressed caches or global reclaim/CPU policies added together | Features compiled into a kernel need not run. Enabling another background mechanism adds its own scanning, metadata and CPU work. | Do not stack KSM, aggressive proactive compaction, DAMON_RECLAIM, a second compressed swap cache or launch-triggered reclaim merely because the phone has 4 GB RAM. The first memory intervention is isolated in [memory-research.md](memory-research.md). |
| Reject | Shrink generic ABI-sensitive constants or remove vendor interfaces for guessed RAM savings | CPU-mask sizes, structure layout, exported symbols and enabled vendor hooks can affect prebuilt module compatibility. | Do not lower `NR_CPUS`, remove drivers/hooks or alter ABI-related settings without a complete module/interface audit. Compilation success alone cannot validate a proprietary module's behavior. |

## What this build can justify

The immediate CPU/I/O work is accurate configuration selection and correction of specific source defects. It does not justify new clock, GPU, thermal, scheduler-delay or disk-scheduler values. Keep the baseline's supported options and allow the ROM to apply its normal runtime policy. KProfiles patch 0003 is separate from the memory intervention. Further SchedHorizon changes remain deferred for a dedicated lifetime/locking review.

The project should retain an unmodified-source reference build configuration alongside the candidate configuration. Record the source commit, toolchain identity, final compiler optimization selection, LTO mode, module/CFI settings, default CPU/I/O governor selections, KProfiles default and thermal-related configuration. Reject an unexpected configuration drop or fallback instead of assuming the defconfig request took effect.

The pinned tree contains no KProfiles callers or notifier clients outside `drivers/misc/kprofiles/main.c` in its C/header sources. This does not rule out consumers in unavailable vendor modules. Patch 0003 preserves exported signatures and assumes that `kp_set_mode()` may have atomic-context callers. Mode updates take effect immediately when allowed by the existing auto-profile/screen checks; listeners run later in process context with the mode sampled by the worker. Consumers must not rely on synchronous notification or on observing every short-lived override. `kp_set_mode_rollback()` still uses its existing sleep and mutex semantics and is not an atomic-context API.

The worker is initialized statically and does not depend on the sysfs object having been created. It uses the existing system workqueue, with no per-event allocation. Mode/override/screen state updates and the active-mode snapshot use the same short spinlock. No blocking listener runs under that lock. Work cancellation is included in the init-error and exit paths. The requested-mode sysfs attribute retains its name, permissions, accepted values and original update-only notification behavior; the patch does not add new sysfs-triggered notifications or change profile defaults.

For the I/O defect review, `dev_to_disk(device)` dereferences `dev_to_bdev(device)->bd_disk`; it cannot be called on the end-of-iteration NULL value. `elv_iosched_store()` returns the input count on success, and the normal queue sysfs path serializes against scheduler changes/unregistration with `q->sysfs_lock` [S13, S14]. These are source-level correctness facts. They do not establish that the user has exercised that otherwise lightly integrated event path.

Patch validation performed here: `git diff --check`, kernel `checkpatch.pl` (zero errors and warnings), reverse-application check, and a comparison of the original/candidate exported names, function signatures, event constant and sysfs attribute. These establish patch hygiene and selected interface preservation, not whole-kernel compilation, general ABI compatibility or device behavior. Full compilation and phone validation must be reported separately.

Hardware acceptance is still unresolved: the device must boot with its vendor modules and preserve calls, camera, Wi-Fi, charging, suspend/resume, video playback and WhatsApp notifications. A build log cannot establish these properties. No percentage speedup, battery saving, thermal improvement or ANR fix should be published before device evidence exists. This review imposes no long benchmark procedure on the user and does not flash anything.
